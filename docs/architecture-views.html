auto-stock-trading 아키텍처 — 6가지 관점

키움 REST API 기반 자동매매 봇을 서로 다른 6개의 렌즈로 본 그림 모음. 같은 시스템이지만 관점마다 보이는 것이 다릅니다.

관점 목록
  1. 논리 계층 — 모듈이 어떻게 쌓여 있고 무엇에 의존하는가
  2. 라이브 매매 루프 — Tick이 어떻게 주문이 되는가 (동작)
  3. 런타임 프로세스 — 맥북에서 실제로 무엇이 도는가 (배치)
  4. 평일 타임라인 — 하루 중 언제 무엇이 겹쳐 도는가 (시간)
  5. 주간 학습 루프 — 운영 결과가 어떻게 전략에 되먹임되는가 (데이터)
  6. 외부 연동 맵 — 어떤 외부 서비스와 어떻게 통신하는가 (통합)
  7. 모듈 의존 그래프 — 실제 import 결합도, 누가 누구에 의존하는가 (코드)
  8. 실거래 가드 — mock→real 전환 시 거치는 안전장치 5단계 (안전)

1. 논리 계층 뷰

렌즈 · 모듈 책임과 의존 방향

위에서 아래로 화살표는 “호출/의존 방향”. 모든 외부 호출은 맨 아래 kiwoom 한 곳으로만 빠져나가고, 맨 아래 부가 4종은 어느 계층에서나 쓰이는 횡단 관심사라 흐름선과 분리했습니다.

2. 라이브 매매 루프 뷰

렌즈 · 동작(behavior) · runner

1~2는 한 번만 도는 준비 단계, 3~6은 봉이 확정될 때마다 도는 루프(왼쪽 괄호). 끝나면 오른쪽 화살표로 다음 봉을 기다립니다. 7번 잔고 갱신은 이 루프와 별개 주기.

3. 런타임 프로세스 뷰

렌즈 · 배치(deployment) · launchd

맥북은 Amphetamine으로 24시간 켜져 있고, 그 위 launchd가 8종 job을 정해진 시각에 실행·자동재시작. 네 묶음 중 paper-day 봇만 장중 상주 프로세스고 나머지 7종은 단발 job입니다.

4. 평일 타임라인 뷰

렌즈 · 시간(temporal)

막대 길이 = 살아있는 시간, 점 = 한 번 실행되는 단발 job, 점선 세로줄 = 개장(09:00)·마감(15:30). 장중엔 봇·snapshot·heartbeat 셋이 겹쳐 돌고, 봇 직전 08:50 marketcap이 종목 풀을 깔아줍니다.

5. 주간 학습 루프 뷰

렌즈 · 데이터 되먹임(feedback)

매주 토요일, 지난주 운영 성과(리포트)와 뉴스를 Claude가 분석해 전략 프로파일(daytrade-current.yaml)을 자동 갱신하고, 그게 다음 주 평일 매매에 반영됩니다 — 운영 → 분석 → 갱신 → 운영으로 닫히는 한 주짜리 루프.

6. 외부 연동 맵

렌즈 · 통합(integration)

시스템이 통신하는 외부 서비스는 넷. 키움만 양방향(시세 받고 주문 보냄)이고, 텔레그램은 알림을 내보내기만, Claude는 주간 분석 요청, RSS는 기사 수신. 각 프로세스가 어떤 서비스에 붙는지 오른쪽에 표시했습니다.

7. 모듈 의존 그래프

렌즈 · 코드 결합도 (실제 import)

src/auto_trading 안의 from ..X import를 전부 센 실측 그래프. 선 두께 = import 횟수(결합도). 세 가지가 드러납니다 — kiwoom은 7개 모듈이 의존하는 단일 sink, cli는 12개를 부르는 최상위 오케스트레이터, strategy는 backtest·daytrade·runner·risk·news 등 6개가 의존하는 공유 판단 코어. 가장 굵은 선은 market→kiwoom(11)·backtest→strategy(8).

8. 실거래 가드

렌즈 · 안전장치 (mock → real)

기본은 KIWOOM_MODE=mock(모의 서버, 진짜 돈 안 움직임). real로 가려면 사용자가 명시해야 하고, 그 뒤로도 주문 하나가 실제 전송되기까지 5단계 관문을 통과해야 합니다. preflight 7종 = risk_limits_active · no_pending_orders · heartbeat_recent · recent_paper_day_mdd · backtest_sharpe · kill_switch_simulation · llm_cost_within_budget.
